**Engineer investigation: BGL, `ciod: failed to read message prefix on control stream`**

## Scope
- Dataset: `bgl` (public Loghub BGL). Requested window [2005-06-01 [r_d91a3550.f12], 2005-07-01 [r_d91a3550.f13]) UTC. BGL data only starts at 2005-06-03T22:42:50Z [r_d915c620.f30], so the time before that has no data, which is not the same as zero events.
- Filter: full-text terms `ciod failed to read message prefix on control stream`. One simultaneity check covers only 2005-06-04, a narrower window that is labelled where it appears.
- Bounded M1 probe: `recurring_patterns`, precursor aggregation and `compare` were not used.

## Answer
It is not one bad node; the symptom is spread across the job. The failures are spread thinly over many I/O nodes in many racks, and they arrive in bursts that hit many racks within the same second or hour. That rules out the idea that the symptoms are confined to one node. It does not rule out a single shared cause, such as the ciod/CioStream peer that every failing line names, or one failed component that many nodes depend on. A second ciod error, `LOGIN chdir(...) failed: No such file or directory`, appears right before the selected event. But by day the two messages only partly line up, so that link stays open.

## Evidence
- Exact population: 5,983 log events [r_d91a3550.f11], all component `APP`, level `FATAL` [r_714cabc0.f2]. The search returned only a bounded set of hits (truncated); frequencies come from `count_events`, not from the hits.
- Selected event `14738` at 2005-06-04T07:24:32Z [r_740eb4a0.f1], node `R23-M1-N8-I:J18-U11`, dataset label `APPREAD` (a dataset label, not our finding):

- Every hit shown names the same peer, `172.16.96.116`, with a different port each time. This is an observation from the sample only, not a counted fact.

## Next check
- **Peer address:** count `172.16.96.116` with the same filters, and pick a burst from another day with `search_logs` sorted by time.
  - If every burst names this peer, a shared-peer origin gains support but is still unproven.
  - If the peer differs between bursts, the single-peer idea is weakened; that alone does not prove separate causes.
- **Job records:** compare the burst start times with the job and partition records for the IP/host behind `172.16.96.116`. Those records are outside this corpus. Only they can tell whether a job ended or a link failed, as opposed to a fault on the service node. Matching timestamps by themselves cannot confirm a cause.
- **chdir link:** run the precursor aggregation (unavailable here) to compare the share of bursts preceded by the chdir message against its base rate.
