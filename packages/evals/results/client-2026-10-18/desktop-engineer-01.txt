## Next check

**Collect evidence from outside these logs.** Pull the job-scheduler / MMCS job records for each burst start: job ID, user, working directory, partition, and how the job ended. Also pull the logs of the service node behind `172.16.96.116` (ciodb / control system) for the same times.

How each outcome would update the hypotheses:
- **Each burst lines up with a job whose working directory is missing:** the launch-side association becomes stronger. It still isn't a proven cause unless the control-stream drop is shown to follow from that job's teardown.
- **Bursts span several unrelated jobs, or the service node logs its own fault or restart:** the shared-component hypothesis gains support and the launch-side link weakens.
- **The burst start without a chdir precursor:** look at it individually (event context on that anchor). A missing precursor there does not show a different or second cause. It only weakens the repeated link.

Whatever the result, a single job-wide origin and a single service-side origin both stay possible until job-lifecycle evidence separates them. Timing and a shared IP alone can't decide between them.

**Inside the log corpus:** run search_logs with `172.16.96.116` over the same window. This shows whether that peer is common to all matches, which tells us how widespread the shared identifier is, but not what caused the failures.
